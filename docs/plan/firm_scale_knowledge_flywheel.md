## 0. 한 문장

**매 평가(engagement)가 법인의 검증 지식을 소비하는 동시에 그 지식을 정련·증식시키는 폐루프를
만든다. 단, 클라이언트 데이터에서 법인 지식으로 가는 흐름은 익명화·집계·승인을 거치는
단방향 밸브 하나만 존재한다.**

핵심 명제 3개.

1. **자산의 본질은 숫자가 아니라 구조다.** "이 산업의 매출을 무엇으로 설명하기로 했는가"는
   마스킹의 대상이 아니라 마스킹 후에 남는 것 그 자체다. → §5-1
2. **재현성이 도구와 조서를 가른다.** 3년 뒤 감리에서 같은 판정이 재현되지 않으면 조서가
   아니다. → §4-1
3. **지식이 코드가 되지 않으면 자산이 아니다**([ax_consulting](ax_consulting_model_quality.md) §11-3).
   본 문서는 그 명제의 역방향 — **평가가 지식이 되지 않으면 축적이 아니다**를 다룬다.

## 1. 출발점 — flywheel의 절반은 이미 돌고 있다

`[실측]` 현재 구조는 **지식 → 규칙 → 평가**(하강) 방향이 완성되어 있다.

| 이미 있는 것 | 실체 |
|---|---|
| 지식 → 규칙 승격 체인 | docs/reference 49챕터 + smic 58케이스 → `checks.py` 게이트 29종(F1~F3·S1~S5 계보) |
| 산업 노하우의 코드화 | `revenue.py` 매출 아키타입 **A~K 11종** + `route_archetype` 라우터 |
| 신뢰도 차등 규율 | rigor 2단 — 권위 골든(비올·클래시스·모델러스)=FAIL 승격 가능 / 학회리포트(SMIC)=WARN prior |
| 자동 동기화 | `.githooks/pre-commit` → 빌드 7종 → `calc_core/data/industry_benchmarks.json` 재생성·동반 커밋 |
| 지식 컴파일러 | `docs/reference/ontology/build.py` — md frontmatter → rag_index.json·graph.json(직접 편집 금지) |

**없는 것은 상승 방향 하나뿐이다.** 평가가 끝나도 그 산출물(가정 원장·게이트 결과·오버라이드
판단)은 `var/projects/{id}.json`에 잠들 뿐 코퍼스로 돌아오지 않는다. 즉 본 문서의 과업은
새 아키텍처 도입이 아니라 **끊어진 반쪽 배관의 연결**이다.

## 2. L0 — 로컬 환류 배관 4개 `[설계]`

법인화 이전, 개인 워크플로우에서 먼저 성립해야 하는 최소 루프.

### 2-1. 케이스 봉인 (핵심 배관)

평가인 트랙 `output` 스테이지에 "케이스 봉인" 스텝 신설. 프로젝트의 **가정 원장**(주장·formula·
값·근거·provenance — [가정원장 방법론](../reference/) 규격 그대로) + 최종 게이트 리포트 +
산업코드·아키타입 태그를 `docs/reference/engagements/`로 내보낸다.

- 디렉터리 구조는 **smic와 동형 3층**: `_fulltext`(사료, 비공개) / `_extract`(기계 추출) /
  루트 md(증류). 기존 gitignore 규약을 그대로 물려받는다.
- 기존 pre-commit 빌드 체인에 합류시키면 벤치마크 집계가 자동으로 살찐다 — **신규 파이프라인
  0본**.

### 2-2. rigor 3단으로 확장

현행 2단 사이에 **"자체 검증 완료 engagement"** 티어를 신설한다.

| 티어 | 원천 | 승격 한도 |
|---|---|---|
| 권위 골든 | 비올·클래시스·모델러스 | FAIL/WARN 규칙 승격 가능 |
| **자체 engagement**(신설) | 게이트 전량 통과 + L1 tie-out 확인 + 사람 봉인 승인 | **WARN prior까지만** |
| 학회리포트 | SMIC | WARN prior(참고) |

`[실측]` 미해결로 기록된 "벤치마크 prior n≥3 산업이 7개뿐"의 **유일한 근본 해법**이 이것이다.
외부 코퍼스는 유한하지만 자체 평가는 계속 쌓인다.

### 2-3. 오버라이드 텔레메트리 = 규칙 정련 신호

사용자가 WARN을 보고도 진행한 기록(규칙 ID·사유·맥락)을 케이스에 남긴다. **반복 오버라이드되는
규칙 = false positive 후보**로 채굴된다. `[실측]` 감린이 레포에서 검증된 패턴(혼동쌍 채굴기:
텔레메트리 → 카드 증식 루프)과 정확히 동형이다.

### 2-4. 아키타입 미라우팅 큐

`route_archetype`이 A~K 어디에도 태우지 못한 케이스를 `unrouted` 큐에 적재. 3건 이상 모이면
아키타입 L 후보로 검토. 매출추정 타이폴로지가 평가를 통해 유기적으로 자란다.

### 2-5. L0 가드 3개 (필수)

| 가드 | 내용 | 위반 시 |
|---|---|---|
| **자기강화 편향 차단** | 자체 engagement 유래 prior는 **영원히 WARN까지만**. FAIL 승격은 골든 검증 + 수동 큐레이션 유지 | 자기 평가 결과를 앵커로 재사용 = ISA 540 경영자편의 우려와 동형인 앵커링 위험 |
| **편입 게이트** | `report.ok=true` + **사람의 명시적 봉인 승인**을 통과한 케이스만 편입 | 결함 있는 평가가 들어가면 flywheel이 오류 증폭기가 된다 |
| **기밀 유지** | smic와 동일 3중 방어(.gitignore + `mask_names.py` fail-closed + public-main) | 공개원칙("귀납지식만 공개·코퍼스 비공개") 붕괴 |

## 3. 법인 스케일 — "DB 하나"가 아니라 저장소 셋 `[설계]`

### 3-1. 왜 하나가 아닌가

`[실측]` 현행 [project_store.py](../../backend/api/project_store.py)는 `projects/{12hex}.json`
평면 네임스페이스에 save/load/list/delete 4연산뿐이다. 법인 레벨에서 이 자리는 **보존기간·접근
주체·기밀등급이 전혀 다른 세 저장소**로 분화한다. 하나로 뭉치면 어느 한쪽의 요구가 다른 쪽을
파괴한다(조서는 불변이어야 하는데 벤치마크는 갱신되어야 하는 식).

### 3-2. 3-store + 단방향 밸브

```
┌─────────────────────────────────────────────────────────────┐
│ [Engagement Store]  계약별 클라이언트 데이터 · 조서          │
│   기밀 최고 / 보존기간 규정 / 팀 단위 ACL / append-only     │
└─────────────────────────────┬───────────────────────────────┘
                              │
              ▼ 단방향 밸브 — 사전 정규화 + k-익명 집계 + 사람 승인 (§5)
                              │
┌─────────────────────────────▼───────────────────────────────┐
│ [Knowledge Store]  벤치마크 · 아키타입 · 케이스 증류         │
│   식별정보 0 / 전사 읽기 / 출처 태그(감사·비감사) 필수      │
└─────────────────────────────▲───────────────────────────────┘
                              │ 읽기 전용
┌─────────────────────────────┴───────────────────────────────┐
│ [Rulepack Store]  게이트 규칙 + 버전 · 발효일 · 승인자 · 계보│
│   불변 릴리스 / 조서에서 버전 핀으로 참조                    │
└─────────────────────────────────────────────────────────────┘
```

**절대 규칙**: Engagement → Knowledge 방향으로만, 그것도 밸브를 통해서만 흐른다. 역방향 원본
흐름은 존재해서는 안 된다. 근거 셋 — ①공인회계사법상 비밀유지의무 ②클라이언트 간 정보 차단
(경쟁사가 같은 법인 고객인 경우) ③감사 독립성(자기가 평가한 값이 자기가 감사하는 회사의
벤치마크가 되면 self-review threat).

`[실측]` 이 밸브의 설계도는 이미 레포에 있다 — docs/reference의 3층 구조(_fulltext / _extract /
증류 md)와 `mask_names.py`의 fail-closed 마스킹. **원료가 SMIC에서 engagement으로 바뀔 뿐이다.**

### 3-3. 부수 이득 — 밸브가 접근통제까지 단순화한다

프라이버시 설계인 줄 알았던 3-store 분리는 **접근통제 설계이기도** 하다. Knowledge Store가
이미 익명화·집계 층이므로 전사 읽기로 열어도 되고, **빡센 ACL은 Engagement Store 한 곳에만**
걸면 된다. 기업 RAG 최대 난제인 ACL 트리밍(§6-4)의 복잡도가 한 저장소에 격리된다.

## 4. 서비스 레벨 요건 `[설계]`

### 4-1. 재현성 3중 핀 — 도구와 조서를 가르는 단 하나의 요건

engagement은 3년 뒤 심리·감리에서 다시 열린다. 그때 "지금 코드"로 재계산하면 **다른 답이 나온다**
— 그동안 규칙이 늘고 엔진이 개선됐을 것이므로.

> 모든 조서 판정은 **(엔진 버전) × (룰팩 버전) × (입력 스냅샷)** 세 개를 함께 각인하고
> 영구 보존한다. "2026-03-12, 엔진 v2.4 · 룰팩 2026.1로 판정했고, 그 조합으로 지금 재실행하면
> 동일 findings가 재현된다"가 성립해야 조서다.

이건 기능이 아니라 **아키텍처 제약**이라 나중에 붙일 수 없다. 룰팩 분리를 규칙 29종 시점에
하는 것과 200종 시점에 하는 것의 비용 차이는 자릿수가 다르다.

### 4-2. 조서 불변성 — 현행 최대 부채

`[실측]` [project_store.py:79](../../backend/api/project_store.py#L79) `save()`는 단순 덮어쓰기다.
지금은 "프로젝트 저장"이지만 법인에서는 **"조서 저장"**이 되고, **덮어쓰기 가능한 조서는 변조
가능한 조서**라 감리에서 증거능력을 잃는다.

이것은 기능 결함이 아니라 **의미론 결함**이다 — 뒤늦게 고치면 이미 쌓인 데이터가 전부 무효가
된다. 마이그레이션 경로는 부록 A.

### 4-3. 인증·인가·독립성

`[실측]` 현행: Cloud Run `--allow-unauthenticated`, 인증 0, 감사추적 0,
`list_ids()`가 버킷 전량 반환(멀티테넌트에 그대로 올리면 전사 프로젝트 목록 노출).

필요: SSO(OIDC/SAML) + RBAC(작성자·리뷰어·EQCR·리스크) + **독립성 체크**(감사팀 ↔ 비감사 데이터
접근 규칙) + 전 조작 감사추적(누가·언제·무엇을 조회·승인·오버라이드했는가 — ISQM 문서화 요구).

### 4-4. 룰 거버넌스 — 잘못된 규칙 하나 = 전사 동시 오류

규칙이 법인 방법론이 되는 순간 배포도 소프트웨어처럼 다뤄야 한다:
**관찰 모드 → 카나리 → 전면 → 롤백**. `[실측]` 이미 문서화된 R3 완화책("신규 규칙은 오탐률
측정 후 승격")이 이 파이프라인의 1단계다.

**경고 피로의 규모 확대**에 유의. 규칙 29종에서 오탐 5%는 견딜 만하지만 200종에서 5%는 매
모델마다 10개의 무의미한 경고다. 등급 인플레이션 금지가 개인 규율에서 **전사 SLA**로 승격돼야
한다.

### 4-5. 현 코드 갭 — 그대로 사는 것 vs 다시 짓는 것

법인화는 전면 재작성이 아니라 **증축**이다.

**그대로 승격되는 것** `[실측]`
- `calc_core` 25모듈이 stdlib-only·IO 0인 순수 결정론 → 상태가 없으니 **테넌트 격리·수평확장이
  공짜**. 부작용을 코어 밖으로 밀어낸 설계가 조직 확장 비용을 미리 지불해 둔 셈.
- provenance의 `source[start:end]==raw_text` 불변식 → 그대로 조서 증적의 원자 단위.
- "게이트는 경고가 아니라 차단" 사상, rigor 2단, 수식 살아있는 xlsx 산출물(도구 종속 회피 R6).
- BYOK·서버 시크릿 0 → 보안심의 통과 자산(강화 대상).

**다시 지어야 하는 것**

| 지금 `[실측]` | 법인 요구 `[설계]` |
|---|---|
| `save()` 덮어쓰기 | append-only 버전 체인 + WORM |
| `list_ids()` 버킷 전량 | 테넌트·engagement·팀 스코프 |
| 인증 0 | SSO + RBAC + 독립성 체크 |
| 감사추적 0 | 전 조작 로그(ISQM) |
| `checks.py` 1,719줄에 규칙 **코드 내장** | 룰팩 **데이터 분리** + 버전·발효일·승인자·계보 |
| `main.py` 2,100줄 단일 파일, Pydantic 0 | 도메인 라우터 분리 + 요청/응답 계약 |

## 5. 익명화 — 무엇이 마스킹을 견디는가 `[설계]`

### 5-1. 마스킹 내성 3계층

`[실측]` **이 공정은 이미 한 번 완주됐다** — SMIC 학회리포트 ~150편에서 개별 기업 숫자를 한 톨도
남기지 않고 매출 아키타입 A~K 11종("모든 매출 = P×Q, Q를 뭘로 두느냐")을 도출한 것이 정확히
"마스킹 → 재포장 → 자산화"의 실증이다. 법인 버전은 원료만 바뀐다.

| 계층 | 내용 | 마스킹 내성 | 처리 |
|---|---|---|---|
| **1. 구조** | 이 산업의 Q를 무엇으로 두는가(조선=수주잔고 소진 / 제약=처방건수×약가 / 게임=DAU×ARPU), 드라이버 트리 분해 형태, 산업별 필수 검증 포인트, 반복 결함 유형 | **손실 0** — 회사명·숫자를 전부 지워도 100% 보존, 오히려 지워야 일반화 | 즉시 자산화 |
| **2. 분포** | OPM·회전기일·CAPEX/매출의 p25/p50/p75, 성장률 감쇠 곡선 실제 형태 | k-익명 집계로 보존(개체 정보 소실 — 애초에 불요) | k 게이트 후 개방 |
| **3. 개별 사례** | "A사는 이런 이유로 이렇게 추정했다"는 서사 | **위험** — 재식별 표면 최대, 가치 대비 위험 나쁨 | 원칙 봉인 또는 패턴으로 추상화해 계층 1로 강등 |

계층 1이 성립하는 근본 이유: **밸류에이션 지식의 가치는 숫자가 아니라 사상(mapping)에 있다.**
`route_archetype` 라우터가 이미 그 형태로 코드화되어 있다는 것이 이 논증의 실물 증거다.

### 5-2. 진짜 난제는 마스킹이 아니라 재식별

회사명 치환은 쉬운 부분이다. 어려운 것은 **숫자 자체가 지문**이라는 사실 — "매출 1조 2,340억 ·
의약품 · 2025년"이면 회사명 없이 특정된다. 산업×연도×규모 세 축만으로 대형 딜은 대부분 좁혀진다.

### 5-3. 핵심 원칙 — 사후 삭제가 아니라 사전 정규화

> **마스킹을 저장 후 처리로 두면 항상 진다.** 절대값이 한 번이라도 Knowledge Store에 들어가면
> 이후 어떤 삭제도 집계값에 남은 흔적을 지우지 못한다.

해법은 **애초에 절대값을 저장하지 않는 것**이다. 매출액 1조 2,340억 대신 "매출성장률 12.3%,
업종 내 규모 p60"만 기록한다. 재식별 표면 대부분이 이 한 수로 사라지고, 밸류에이션에서는
**공짜다** — 어차피 재사용 가치가 있는 것은 비율과 순위지 절대 규모가 아니다.

`[실측]` 이 사상은 `mask_names.py`가 fail-closed인 것과 동일하다: 게이트를 인제스트 지점에 둔다.

### 5-4. 통계적 방어 2종

- **최소 셀 크기(k-익명) + 셀 억제**: 표본 k 미만 산업은 공개하지 않고 상위 분류로 롤업.
  국내 대형 조선처럼 모집단 자체가 3사인 산업은 법인 스케일에서도 k를 못 채우므로, **구조
  (계층 1)만 남기고 분포(계층 2)는 포기**하는 것이 맞다.
- **차분 공격 방어**: 분기 간 벤치마크 차이로 신규 편입 1건을 역산할 수 있다(n이 작을수록 치명).
  실무 해법 = 갱신을 실시간이 아닌 **배치**로 묶고, 편입 건수가 임계 미만이면 갱신 자체 보류.
  차분 프라이버시식 노이즈 주입은 **채택하지 않는다** — 판정 근거로 쓸 숫자에 인위적 노이즈를
  넣으면 조서에서 설명이 안 된다.

### 5-5. 출처 태그 — 소급 제거 가능성

Knowledge Store의 모든 항목에 출처 태그(감사/비감사, 상장/비상장, 동의 여부, 편입 시점)를 달지
않으면, 나중에 특정 클라이언트 데이터를 소급 제거해야 할 때(계약 종료·이의 제기) **집계값에서
걷어낼 방법이 없다.** 집계는 원본을 지워도 남는다 — 설계 시점에만 해결 가능하다.

### 5-6. 기술보다 먼저 — 계약

솔직한 병목은 기술이 아니다. **engagement letter에 "익명화·집계된 형태로 방법론 개선 목적에
사용할 수 있다"는 조항이 있는가**이다. 없으면 k-익명성을 완벽히 구현해도 계약 위반이라 못 쓴다.
반대로 조항이 있으면 **계층 1(구조)은 사실상 논쟁 없이 자산화된다** — 판단 구조는 클라이언트
정보가 아니라 법인의 전문가적 판단이므로.

## 6. 연결 기술 — 하나가 아니라 성격별 3층 `[설계]`

### 6-1. 성격별 분기 (이 분기를 틀리는 것이 기업 RAG 실패의 전형)

### 6-2. 절대 규칙 — 숫자는 벡터 검색으로 가져오지 않는다

RAG로 벤치마크를 조회하면 같은 질의가 다른 답을 낼 수 있고, 그 순간 §4-1 재현성이 무너진다.
이것은 [ax_consulting](ax_consulting_model_quality.md) §7 **R2("AI가 숫자를 만드는 것")의 변종**이며
실제로는 더 잡기 어렵다 — RAG는 출처를 보여주므로 **재현 불가능한데도 근거가 있어 보인다.**

### 6-3. 구체 스택 (M365 E5 테넌트 기준 — 대형 법인 대부분)

| 층 | 기술 | 유의점 |
|---|---|---|
| 인증·인가 | Entra ID(구 Azure AD) OIDC/SAML SSO | 다운스트림 접근은 서비스 계정이 아니라 **OBO(on-behalf-of)** — 사용자 토큰 위임이라야 권한 우회가 없다 |
| 문서 수집 | Microsoft Graph API(SharePoint/OneDrive/Teams) | **Microsoft Purview 민감도 라벨을 존중** — 무시하면 라벨 체계를 우회하는 도구가 된다 |

### 6-4. ACL 트리밍 — 기업 RAG 최대 난제

사용자가 볼 권한 없는 조서가 답변에 인용되면 그 자체로 사고다. 다만 §3-3대로 **Knowledge
Store는 이미 익명화 층이라 전사 읽기**로 열 수 있고, 엄격 ACL은 Engagement Store에만 필요하다.

### 6-5. 현 레포 변경 지점 — 의외로 작다

`[실측]` [backend/rag/](../../backend/rag/)는 `searcher.py` 250줄 + `embedder.py` 153줄
(+ `__init__.py` 12줄, 모듈 총 415줄)뿐이다. **구조는 그대로 두고 임베딩 백엔드 교체 +

더 중요한 것은 `docs/reference/ontology/build.py`의 **컴파일 패턴** — md frontmatter에서

## 7. 법인 스케일 flywheel — 폭발력과 함정 3

### 7-1. 폭발력 — 벤치마크가 감사 증거가 되는 지점

`[실측]` 현행 미해결 "벤치마크 prior n≥3 산업이 7개뿐"이 해소된다. `[가정]` 대형 법인은 연간
수백 건의 밸류에이션·손상·PPA를 수행하므로 3년이면 산업별 표본이 통계적으로 유의해진다.

여기서 **질적 전환**이 일어난다. ISA 540(회계추정치 감사)에서 감사인은 경영자 가정에 대한
독립적 기대치를 형성해야 하는데, 현행 `analytical.py`의 `consensus_anchor`가 외부 컨센서스에
의존하는 그 자리를 **법인 자체 코퍼스가 대체·보강**한다.

> "이 회사의 추정 영업이익률 18%는 우리가 검증한 동종 47건의 p75를 상회한다"
> — PDF 체크리스트로는 절대 만들 수 없는 감사 증거.

### 7-2. 함정 3

| 함정 | 기전 | 방어 |
|---|---|---|
| **자기참조 순환** | 우리가 평가한 값이 벤치마크가 되고 그 벤치마크로 다시 평가 → 코퍼스가 시장과 무관하게 표류 | 상시 외부 앵커 대조(주가·거래사례·컨센서스). 분포가 시장 관측치에서 이탈하면 **그 자체가 경보**. §2-5 "자체 유래는 WARN까지만" 유지 |
| **경고 피로의 규모 확대** | 규칙 200종 × 오탐 5% = 모델마다 무의미한 경고 10개 | 등급 인플레이션 금지를 전사 SLA로. 신규 규칙 관찰 모드 의무 |
| **지식의 출처 오염** | 출처 태그 없이 집계하면 소급 제거 불가 | §5-5 출처 태그 필수 + 감사/비감사 사용 제한 |

## 8. 레벨 로드맵 `[설계]`

| 레벨 | 상태 | 핵심 추가 | 완료 판정(DoD) |
|---|---|---|---|
| **L0 개인**(현재) | 워크북 정본 + 3창구 분업([addin](addin_two_panel_ux.md) §9) | GCS 영속화 · §2 환류 배관 4개 | 왕복 diff 기준선이 재시작에 생존 / 봉인된 케이스가 pre-commit 체인을 타고 벤치마크에 반영 |
| **L1 팀** | 공유 프로젝트 + 리뷰 워크플로우 | 인증·RBAC · 조서 버전 체인 · 제출→검토→승인 상태기계 | 두 사람이 같은 모델을 놓고 지적·해소 이력이 남는다 |
| **L2 법인** | 룰팩 거버넌스 + 지식 환류 | 룰팩 분리·버전 핀 · 3-store + 단방향 밸브 · 감사추적 · ISQM 조서 출력 | **3년 전 조서를 그때 룰팩으로 재현 성공** |
| **L3 방법론 자산화** | 법인 코퍼스가 독립적 기대치를 공급 | 벤치마크 임계질량 · ISA 540 연계 · 외부 앵커 상시 검증 | 게이트가 "우리 47건 대비"로 판정한다 |

**순서 규율**: L1과 L2 사이에 강한 선후가 있다 — **조서 불변성과 인증이 지식 환류보다 먼저**다.
데이터가 쌓이기 전에 밸브를 다는 것이 아니라, **밸브를 달기 전에 조서 무결성을 세운다.** 오염된
조서에서 나온 지식은 flywheel이 아니라 오류 증폭기다.

## 9. 최종 종착지

**법인의 밸류에이션 방법론이 문서가 아니라 실행 가능한 코드로 존재하고, 매 engagement이 그
방법론을 적용하는 동시에 검증·정련하는 폐루프.**

조직 관점의 변화가 본질이다.

| | 현재 | 종착지 |
|---|---|---|
| 방법론 개정 | 심리실이 PDF를 개정 → 교육 배포 | **룰팩 릴리스** |
| 적용 | 사람이 읽고 기억해야 적용 | 배포 즉시 전사 모델이 새 기준으로 검사됨 |
| 증명 | 적용했다는 진술 | 적용 여부가 **로그로 증명** |

제품 형태는 [addin](addin_two_panel_ux.md) §10-2의 결론(①엑셀 함수 애드인 + ②검증 게이트웨이,
웹 UI는 관리 대시보드로 축소)이 유효하다. 법인 레벨에서 **③지식 서비스 레이어**가 추가된다 —
벤치마크·아키타입·룰팩을 조회하는 내부 API. 이것이 있어야 애드인 함수
(`=VS.BENCHMARK("의약품","OPM","p75")`)와 게이트웨이가 **같은 정본**을 본다.

### 9-1. 냉정한 관점 — 진짜 자산은 소프트웨어가 아니다

`[실측]` 엔진 5,410줄과 게이트 29종은 유능한 팀이면 복제한다. 복제 불가능한 것은 **누적된
engagement 코퍼스**와 **각 규칙에 달린 계보**(이 규칙은 어느 심리 지적, 어느 실패 사례에서
나왔는가)다.

현행 룰 ID 계보 관리(R1~R16 모델러스 / D1~D7 결함 / E·J 비올 / F1~F3 승격 / S1~S5 칼럼)가
법인 스케일에서 그대로 해자가 된다. **코드는 카피되지만 계보는 카피되지 않는다.**

## 부록 A. 마이그레이션 경로 — `project_store` 조서화 `[설계]`

현행 4연산을 깨지 않고 증축하는 경로(기존 호출부·테스트 무영향 원칙은 현 모듈 docstring의
설계 철학 그대로).

1. **버전 접미 도입**: `projects/{pid}.json` → `projects/{pid}/v{n}.json` + `HEAD` 포인터.
   `load(pid)`는 HEAD를 읽으므로 **호출부 시그니처 불변**.
2. **save를 append로**: 새 버전 파일 기록 → HEAD 갱신. 기존 버전은 절대 덮어쓰지 않는다.
   GCS 객체 버저닝 + 보존 정책(Bucket Lock)으로 WORM 강제.
3. **판정 핀 부착**: 저장 payload에 `engine_version` · `rulepack_version` · `input_digest`(입력
   해시) 3필드 추가. 이 시점부터 §4-1 재현성이 성립.
4. **스코프 도입**: `_PREFIX = "projects/"` → `tenants/{tid}/engagements/{eid}/`.
   `list_ids()`가 스코프 인자를 받도록 변경(현행 버킷 전량 반환은 멀티테넌트에서 정보 노출).
5. **감사추적 분리 스트림**: 조회·승인·오버라이드는 조서 본문이 아니라 별도 append-only 로그로.

**호환성 실패 의미론**은 현행 원칙 유지 — GCS 실패를 삼키지 않는다(`StoreError`). "영속됐다고
믿는" 최악의 형태가 조서 층에서 발생하면 피해가 훨씬 크다.
